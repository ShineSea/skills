# PPT 制作：模式、逐页设计与实现

创建或修改完整网页 PPT 时必须读取本文件。内容输入（页面规划稿或现成大纲）是设计起点：有规划稿时，根据规划稿及其内容依据设计每一页；直接拿到大纲时，根据大纲设计每一页。无论哪种入口，每页的最终内容、布局、视觉风格和动效都在本文件描述的过程中一起决定。

## 模式选择

根据任务选择模式。不要因为已有文件就自动选择修改模式，也不要因为用户提出较大改动就自动重做整套演示文稿。

### 创建模式（Create Mode）

当用户要求根据源文档、页面规划稿、现成大纲、资料、风格提示词或参考图创建一套新的网页 PPT 时使用。

核心流程：

1. 确认输入类型和交付范围。若只有源文档，先按 [page-planning.md](page-planning.md) 生成页面规划稿；若已有规划稿或大纲，以它为起点；若两者都有，按用户指定的权威来源核对差异。
2. 读完整份规划稿或大纲，理解业务逻辑、信息依赖和叙事主线，区分事实来源与附带的写作或排版指令。
3. 分析目标、受众、场景和参考图，提炼视觉语言与约束。
4. 规划整套叙事和节奏，确定章节与页数。
5. 逐页联合设计内容与视觉：决定每页最终上屏的内容、布局、图形与动效。
6. 从已经设计的页面中提取真正重复的模式，建立 Design System 和组件。
7. 按本文件“Reveal.js 实现要求”实现完整网页 PPT。
8. 按 [acceptance.md](acceptance.md) 渲染、验收并修复，直到通过。

### 修改模式（Revise Mode）

当用户要求修改、扩展、重构、统一或升级已有网页 PPT 时使用。

核心流程：

1. 检查现有演示文稿的源文件、资源、页面结构和实际渲染结果。
2. 识别已有 Design System、重复组件、特殊页面和设计意图。
3. 明确用户要求、不可改变的内容和预期结果。
4. 判断修改影响范围：局部页面、共享组件、全局系统或叙事结构。
5. 只重构完成修改所需的范围，同时保持未涉及部分稳定。
6. 更新 HTML、CSS、JavaScript、内容或素材。
7. 按影响范围重新渲染并执行相应验收。
8. 共享或全局变化必须进行跨页回归检查。
9. 修复发现的问题并再次渲染，直到最终验收通过。

如果任务同时包含新建页面和修改已有页面，以修改模式为主；对新增页面应用创建模式的内容规划和逐页设计原则。

## 分析用户意图与视觉参考

开始设计或修改前，将需求转化为明确标准：

- 核心信息与期望的受众反应
- 受众知识水平和演示场景
- 语气、能量、密度与正式程度
- 品牌要求与视觉限制
- 必须保留的内容、顺序和强调重点
- 页数、节奏和演示时长
- 修改模式下的保留范围与目标变化

分析参考图或参考演示文稿时关注可迁移的视觉特征：构图、对齐与留白；字体、字号反差和层级；色彩关系与背景处理；图形语言、边框、阴影和纹理；摄影、插画和图标风格；信息密度和图表表达；Logo、页码、页眉、页脚等 chrome；转场与动效特征。

将参考拆成可迁移的设计规则（色彩、光感、字级、留白、线条、图标和图形质感），另列出仅属于参考画面的具体布局和内容模块。除非用户明确要求复刻，后者不能机械搬到其他页面。检查多页是否只是替换标题和文案：若是，就回到内容关系重新设计。

参考与常规设计习惯冲突时，优先遵循用户的明确要求和参考中最稳定的共同特征。

## 创建模式：规划整套演示

内容规划稿是详实的内容起点，不是最终页面脚本或设计规格。开始制作前先整体理解规划稿或大纲，确定演示的开场、展开、收束、章节关系、节奏和关键页面。

在整套层面为每页确定页码、工作标题、沟通目的和受众应记住的结论，作为逐页设计的锚点；具体的内容取舍、信息层级、视觉结构和动效判定在逐页设计阶段完成（见下节），不在此重复展开。

从整套演示层面检查：开场、展开与结尾是否清晰；页面之间的逻辑过渡是否自然；节奏和信息密度是否均衡；安静页面与密集页面是否有意交替；视觉变化是否足够且仍保持统一身份；关键观点是否获得足够强调；规划稿或大纲是否完整覆盖。

不要先建立“标题页、双栏页、三卡片页、引用页”等固定模板，再把内容分配进去。先确定每页需要传达什么，再决定最合适的结构。总览、流程、并列类别、趋势、台账和空间关联不能因为同属一章就共享相同布局。

## 创建模式：逐页设计内容、布局、视觉与动效

真正制作每一页时，把内容和视觉作为一个不可分割的设计问题重新规划，而不是先锁定文案、再为它寻找容器。对每页同时完成：

- 从规划稿（及其内容依据）或大纲重新确认本页沟通任务与事实边界。
- 决定观众最终应记住的结论，以及哪些内容保留、合并、精炼、移入图形、移至别页或拆成新页。
- 编辑最终上屏的标题、正文、数字、标签、限定条件和来源。
- 识别最终内容之间的流程、对比、层级、因果、空间或证据关系。
- 根据这些关系决定信息层级、构图、图形、图表、图片和素材。
- 同步完成本页动效设计：判定为必需、可选或静态并给出内容理由；为判定动效的页面明确初始状态、进入顺序、触发方式、中间状态和最终状态，以及动效要解释的顺序、因果、层级或注意力转移。
- 检查视觉方案是否反过来帮助内容更准确、更清楚，而不是迫使内容适应预设模板。

动效是每页设计交付的一部分，与内容、布局、视觉同时决定，不允许全部页面设计完再统一补动画，也不允许到实现阶段才补判。标记为必需的页面在实现中必须有对应的元素级动效；判定细节和实现要求见本文件“动效设计”一节。

逐页决策可以直接落实到页面源文件中，不要求另建一份与规划稿重复的设计文档。设计改变时直接修改源文件；只有事实、页面主题、内容范围或关键结论发生实质变化，或用户明确要求同步时，才回写内容规划稿。

每页应做到：

- 建立一个清晰视觉焦点，保持明确阅读顺序。
- 用比例、位置、对比和空间表达层级；聚合相关信息，分隔无关信息。
- 能用图形关系表达时减少大段文字；让文字承担图形无法承担的含义。
- 保留关键事实、限定条件、标签与单位；图表和图解服务于理解，不作为装饰。
- 让图标、形状、箭头、线条和色彩表达分类、方向、状态或强调，构成可识别的设计语言；避免只有深色背景与矩形卡片。
- 控制无关装饰，保证演示距离下的可读性。

允许主张页、编辑式分栏、流程、对比、时间线、系统图、数据故事、案例、带标注图片或全幅视觉使用不同结构，但必须共享一致的视觉身份。

逐页自问：如果去掉标题，这个布局是否仍能表达本页独有的关系？如果只是将另一页的卡片换词，则重新设计。

内容溢出时，不要简单缩小全部文字。根据用户允许的范围精炼文字、重新布局、拆分页面，或在页数允许时增加页面。省略号、`text-overflow: ellipsis` 和固定长度截断不是演示文案的解决方案。

## 首页与结尾页

首页必须建立第一视觉重点、核心命题和演示身份，不能只是标题容器。应体现用户主题和参考方向，但不要堆叠摘要、目录和多组次要信息。

最后一页必须完成内容收束并自然表达感谢。根据任务可包含结论、行动方向、联系方式或一句与主线相关的结束语，但不能只有孤立的“谢谢观看”，也不能新增材料没有支持的承诺。

## 创建模式：完成设计后提取组件

所有页面已有明确构图后，再比较它们并识别真正重复的模式，例如标题与标签处理、反复出现的数据或引用、图片框与说明文字、图表图例与图解节点、Logo 与页码页脚、不会迫使内容变形的重复布局结构。

将这些模式实现为 CSS 类、自定义属性、小型 HTML 结构或必要的 JavaScript helper。不要为了抽象而建立比演示文稿本身更复杂的组件系统。独特页面可以保持独特。

## Design System

创建模式在完成逐页设计后建立 Design System；修改模式从已有实现中识别并按用户需求更新它。

- **画布与网格**：1920 × 1080、16:9 画布；定义安全边距、内容边界、列、沟槽和基础间距；关键内容远离画布边缘；保持共同对齐锚点，同时允许页面使用不同构图。
- **字体**：定义展示字、页面标题、章节标题、正文、图注、数据标签和脚注层级；控制字体家族和字重数量；保持适合投影观看的行长、行高与间距；避免孤行、异常换行、字符裁切和过小标签；确保字体可靠加载并提供 fallback。
- **色彩**：定义背景、表面、正文、次要文字、强调、状态和数据系列颜色；真实渲染中保持足够对比度；用强调色表达意义和重点；同类数据跨页重复时保持颜色语义一致。
- **间距与形状**：建立统一间距尺度；对圆角、描边、分隔线、阴影和图标处理建立规则；定义图标线宽、箭头形态、连接线、强调线与光效的使用语义，按内容关系组合，而非只换色复用同一排版。
- **全局 Chrome**：统一 Logo、页码、章节标识、页脚、来源行和进度提示的位置、尺寸、透明度和安全区行为；只使用符合用户场景的 chrome；同一信息避免重复出现，页码、章节号和业务步骤号明确区分；封面、全幅视觉和章节页可按构图目的隐藏或调整 chrome。
- **图像与数据可视化**：统一图片裁切、遮罩、边框、叠加和图注方式；除非设计明确需要，保持图片比例；保持摄影、插画和图标方向一致；图表必须有可读的轴、单位、标签、图例和来源；直接标注能减少查找成本时优先直接标注。
- **全局动效规范**：统一整套演示的翻页转场（类型、时长、缓动）和 fragment 默认行为；为同类型动效建立统一的运动语言——例如所有流程推进、图表绘制、时间线进入、元素强调分别使用一致的进入方式、时长量级和缓动曲线，不因页面不同而随意变化。每页动效的具体编排仍以该页内容关系为准，但同类动效必须在全局规范下保持可识别的统一风格；返回重播、深链初始状态和 `prefers-reduced-motion` 降级行为也按全局规则一致执行。

一致性不等于相同布局。整套演示应具有共同身份，同时允许每个观点使用最适合它的构图。

## 动效设计

逐页设计时将动效判定为**必需**、**可选**或**静态**，并记录理由。该判断属于页面设计过程，不要求写回内容规划稿。

- 页面包含流程、时间线、因果链、层级展开、关系网络、数据流、图表增长、地图路径、步骤操作或前后状态变化时，元素级动效原则上为**必需**；若保持静态，应能说明运动为何不会改善理解或会破坏演示场景。
- 封面、单一主张、简短结论、法律声明或本身一眼可读的静态构图可以保持静态；不为数量指标添加装饰性运动。
- 只要整套演示中存在“必需”页面，最终实现就不能只有全局翻页转场，必须包含与页面内容对应的元素级动效。

动效语法：

- 流程按步骤推进；关系图先出现核心再建立连接；图表先建立坐标或基线再展示数据；时间线按事件顺序进入；前后状态让变化对象明确可比。
- 同一时刻只让当前叙事焦点运动，其他必要上下文可以预显；避免所有元素同时漂移、缩放或淡入，也避免用不同动画样式制造无关视觉噪声。
- 动效不暗示未经证实的数据更新、状态变化或产品交互；动画结束后的文字、数字、位置和尺寸必须与静态最终版一致。

动效实现要求：

- Reveal.js 的页面 `transition` 只属于翻页效果，不能计作内容动效。
- 离散步骤优先使用 `.fragment` 和明确的 fragment 顺序；连续路径、进度、连线或图表绘制可使用 CSS、Web Animations API 或 SVG stroke 动画。
- 触发绑定 Reveal 的 `ready`、`slidechanged`、`fragmentshown`、`fragmenthidden` 等可靠事件，不依赖固定延时猜测页面是否已出现。
- 用可识别的类或数据属性记录状态，例如 `data-motion="required"`、`data-motion-step`，便于自动检查声明与实现一致。
- 返回动效页时应能正常重播；直接访问 hash 深链时得到正确初始状态；快速连续翻页不能让元素卡在半完成状态。
- 必须支持 `prefers-reduced-motion`：开启时页面直接显示完整、可读的最终状态，而不是隐藏 fragment 内容。
- 不用视频或 GIF 代替本应由页面结构表达的流程动效，除非素材本身就是用户要求展示的证据。

## 修改模式：检查现有演示

修改前先检查源文件和渲染结果，不要只依据代码猜测当前视觉效果。

检查内容包括：Reveal.js 初始化配置与页面层级；HTML、CSS、JavaScript 和资源目录结构；页面数量、顺序、fragment 与转场；字体和外部资源的加载方式；共享样式、局部样式和复用组件；内联覆盖、重复规则或特殊页面逻辑；当前渲染中的溢出、裁切、错位或资源失败；用户要求修改内容与现有实现之间的关系。

先建立当前状态基线。已有异常若会影响本次修改或最终验证，应一并处理；无关问题可以记录，但不要擅自扩大修改范围。

## 修改模式：识别已有 Design System

从代码和实际页面中提取当前设计系统：画布尺寸、安全区、网格与对齐锚点；字体层级、字重、行高与字距；背景、表面、正文、强调色和数据色；间距、圆角、描边、阴影与形状语言；图片比例、裁切、遮罩和说明方式；Logo、页码、页眉页脚、章节标识与来源信息；转场、动画时长、缓动和 fragment 行为；经常重复的组件以及故意独特的页面。

区分三种情况：

- **稳定规则**：多页一致出现，应继续遵循。
- **有意例外**：为封面、章节页、全幅视觉或关键页面服务，应保留其目的。
- **历史不一致或缺陷**：没有明确设计目的，应在修改范围允许时修正。

不要用本 Skill 的默认偏好覆盖成熟的已有系统。只有用户明确要求视觉升级，或现有规则造成实际问题时，才修改 Design System。

## 修改模式：判断影响范围

修改前将任务归入下列范围，并据此决定实施与验收强度：

- **局部页面修改**：文字纠正、单页换图、局部排版或单页动效调整，且不改变共享规则。修改目标页面源文件，渲染并检查所有受影响页面；若影响前后节奏，再检查相邻页面和 contact sheet。
- **共享组件修改**：多个页面共用的组件、图表结构、卡片、标题或 chrome。找出所有使用页面，更新共享实现，重新渲染这些页面并检查跨页一致性。
- **全局 Design System 修改**：字体、颜色、间距、网格、Logo、背景、全局 chrome 或通用动效。明确新规则及其例外，更新设计 token 与共享样式，重新渲染全部页面并重新生成 contact sheet。
- **叙事或结构修改**：增删页面、调整章节顺序、改变故事线、拆分或合并内容。为受影响部分重新规划，用创建模式的逐页设计原则处理新增或重构页面，检查页面编号、导航、章节标识和内容映射；顺序或全局节奏改变时重新渲染整套演示。

如果影响范围不确定，按可能受影响的最大合理范围执行检查和验收。

## Reveal.js 实现要求

使用语义清晰的 HTML、可维护的 CSS 和完成效果所需的最少 JavaScript。Reveal.js 按以下目标配置：

```js
Reveal.initialize({
  width: 1920,
  height: 1080,
  margin: 0,
  minScale: 0.1,
  maxScale: 2,
  hash: true,
  center: false
});
```

实现必须：

- 包含规划的全部页面和必要内容；默认使用水平页面，除非用户明确需要垂直嵌套。
- 用 CSS 自定义属性表达真正重复的设计 token，并限制演示专用样式的作用范围。
- 保持合理 DOM 顺序和文本可访问性；信息性图片提供有意义的替代文本，装饰图片不干扰阅读顺序。
- 稳定布局方式可用时避免脆弱的绝对定位；艺术化构图需要时可有意使用绝对定位。
- 避免与结果无关的依赖；字体与资源加载完成后正确呈现，加载失败时显示经过设计的替代状态。
- 不保留占位图、lorem ipsum、未完成注释、空容器或虚构数据。
