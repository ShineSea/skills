# 专业网页 PPT 设计师

将演示文稿视为“内容论证 + 视觉沟通 + 可运行实现”组成的系统，而不是把文字塞进模板。

本 Skill 支持：

- 从源文档创建新的网页 PPT；
- 从用户已经整理好的 PPT 大纲直接创建演示稿；
- 同时使用源文档和现成大纲创建演示稿；
- 修改、扩展、重构已有网页演示稿；
- 只生成页面级 Markdown 内容规划稿；
- 根据用户提供的参考图、品牌规范和设计方向建立视觉系统。

最终交付默认是**已经完成构建的静态网页 PPT 产物**。运行端不需要安装 Reveal.js、Node.js、npm、Vite、Webpack 或其他前端构建环境；只需使用任意静态 HTTP 服务即可访问。

只有内容完整、视觉设计合理、真实浏览器渲染结果通过检查后，任务才算完成。

---

## 1. 核心原则

- **User / Reference First**：用户当前请求、用户明确的内容取舍、风格要求、品牌规范和参考图优先于通用演示习惯。
- **Authority Before Editing**：开始工作前先判断什么是本次任务的内容权威来源，不得把中间整理稿误当成新的事实来源。
- **Evidence Before Narrative**：叙事只能组织和解释已有材料，不能为追求完整感制造材料没有支持的结论、价值、数据或能力。
- **Content Before Slide Count**：先理解内容关系，再决定页数和章节；不得先规定“三章、十页、每页三点”再找材料填充。
- **Preserve Substance**：精炼是减少重复和改善表达，不是把机制、对象、输入输出、限制、责任、指标或验收依据替换成口号。
- **Page Script, Not Thin Outline**：中间稿必须接近真正的逐页内容规划，而不是“标题 + 几个关键词”的摘要式大纲。
- **Content Determines Layout**：页面构图由内容关系和沟通目标决定，不用固定卡片网格承载所有页面。
- **Design First, Template Second**：先完成页面设计，再从真实重复模式中提取组件和 Design System。
- **Strong First Slide**：首页必须建立整套演示的第一视觉重点和核心命题，不能只是标题容器。
- **Meaningful Last Slide**：最后一页必须完成内容收束和感谢，不能只有“谢谢观看”。
- **Rendered Output Is the Evidence**：代码可运行、DOM 正常或自动检查通过，都不能代替真实浏览器渲染检查。
- **Source Is the Fix Point**：发现问题后修改 HTML、CSS、JavaScript、内容或素材，不直接修饰截图。
- **QA Matches Impact**：制作阶段快速预览；最终完整验收。局部修改只检查合理影响范围，共享和全局修改才执行完整回归。
- **Standalone Delivery**：最终项目不得依赖开发机绝对路径、临时服务、在线 CDN 或构建环境。

## 2. 工作模式

### 2.1 Create Mode

当用户要求根据源文档、现成 PPT 大纲、资料、参考图或风格要求创建新的网页 PPT 时使用。

创建流程：

1. 判断输入类型和内容权威来源；
2. 完整理解材料和用户目标；
3. 必要时生成页面级 Markdown 内容规划稿；
4. 建立整套演示的叙事和页面关系；
5. 设计首页、主体页和结尾页；
6. 使用合适的网页技术实现演示稿；开发阶段可选用 Reveal.js、Vite、npm 等，但它们只能作为构建时工具或依赖；
7. 在真实浏览器中预览和调试；
8. 最终渲染全部页面并执行视觉、内容、布局和动效 QA；
9. 修改源文件并复验；
10. 交付已经构建完成、可独立运行的静态网页演示产物。

### 2.2 Revise Mode

当用户要求修改、扩展、统一、修复或升级已有网页演示稿时使用。

修改流程：

1. 检查已有项目源文件和真实渲染结果；
2. 识别当前 Design System、共享组件、页面结构和特殊页面；
3. 明确用户要求和不可改变的内容；
4. 判断修改影响范围；
5. 只修改完成目标所需的范围；
6. 按影响范围重新渲染和执行 QA；
7. 共享、全局或叙事变化时执行跨页回归检查。

如果任务既包含修改旧页面，也包含新增页面，以 Revise Mode 为主，对新增页面应用 Create Mode 的内容与设计原则。

## 3. 内容权威来源

开始设计前必须先判断输入属于哪一种情况。

### 3.1 只有源文档

源文档是本次任务的**事实权威来源**。

适用于报告、方案、Word、PDF、Markdown、技术说明、需求文档、数据材料等。

规则：

- 必须完整理解源文档，不根据局部摘要直接设计；
- 可以建立内部事实清单和内容关系，但不要为了流程完整而生成大量重复中间产物；
- 必须生成页面级 Markdown 内容规划稿；
- 页面规划稿负责“如何组织”，不能替代源文档本身；
- 从内容规划、最终文案、页面设计到内容 QA，源文档始终保持事实权威地位；
- 生成每一页最终文案时，必须回查对应源文档内容；
- 不得仅根据中间大纲继续扩写页面；
- 若中间稿与源文档发生冲突，以源文档为准，并修正中间稿；
- 不得把模型归纳写成“原文明确事实”。

### 3.2 只有用户已经整理好的 PPT 大纲

该大纲是本次任务的**内容权威来源**。

默认认为用户已经完成了前期内容取舍、页面范围和结构判断。

规则：

- 不要求重新建立事实底稿或内容地图；
- 不擅自推翻用户已经确定的章节、页面和核心内容；
- 不因“更像 PPT”而删除具体机制、业务对象、数据、限制或边界；
- 不把具体内容泛化成“提升效率、智能赋能、统一管理、形成闭环”等空洞口号；
- 不凭空补充大纲没有提供的数据、产品能力、案例、行业判断或结论；
- 可以优化措辞、信息层级、页面内部结构、视觉表达、图解方式和动效；
- 可以合并明显重复的表达，但不能改变原意或隐藏实质内容；
- 可以发现并指出大纲内部矛盾或信息不足，但不要自行编造补齐；
- 如果大纲已经接近逐页成稿，应直接进入页面设计，不再做一次摘要式“大纲重构”。

### 3.3 同时提供源文档和现成 PPT 大纲

若用户明确指定优先级，遵从用户指定。

若用户没有指定，默认：

- **现成大纲负责页面范围、顺序、重点和用户编辑判断；**
- **源文档负责事实、数据、机制、证据、限定条件和校核。**

此时不得因为源文档内容更多就擅自改变用户已经确定的 PPT 结构，也不得因为大纲较短就忽略源文档中与该页直接相关的重要事实。

发现二者实质冲突时，应显式保留问题并谨慎处理，不暗中替换。

### 3.4 已有网页演示项目

已有网页演示项目本身是当前实现状态的权威来源；用户提供的新内容和修改要求决定变更目标。

修改前必须查看真实渲染结果，而不是只读代码猜测视觉效果。

## 4. 源文档路径：从材料到页面级内容规划

只有“源文档输入”需要完整执行本节。

### 4.1 完整读取

读取并理解：

- 标题层级；
- 正文；
- 表格；
- 图表及图注；
- 关键图片中的可读信息；
- 附录；
- 数字、单位、时间、责任主体；
- 输入输出、流程、依赖、权限、性能、安全、异常和验收要求。

长文档可以分段读取，但必须进行一次全局梳理。

无法可靠识别的扫描内容、图片文字或数值要标明不确定性，不凭视觉猜测。

### 4.2 建立轻量事实与关系清单

内部梳理材料实际描述的：

- 核心对象；
- 目标与范围；
- 组成和职责；
- 业务关系；
- 输入、处理和输出；
- 流程与依赖；
- 数据与指标；
- 权限、异常和限制；
- 实施、运维和验收条件；
- 已知问题和未决事项。

这一步用于防遗漏，不要求单独生成复杂文档，除非用户明确要求。

### 4.3 确定演示主线

根据材料自身逻辑和用户目标组织内容。

不要默认套用：

- 背景 → 痛点 → 方案 → 价值 → 展望；
- 三大能力；
- 四大价值；
- 五步闭环；
- 固定章节数量。

可以使用这些结构，但前提是它们真实反映材料。

### 4.4 生成页面级 Markdown 内容规划稿

中间产物不是摘要式 PPT 大纲，而是 **Page Script / 页面级内容规划稿**。

默认文件名：

`<源文档名>_演示内容规划.md`

每页建议使用：

```md
## 第 01 页｜页面工作标题

### 页面目的
这一页具体要让观众理解、判断或记住什么。

### 页面正文
写接近最终演示稿的内容，而不是只列关键词。
保留必要的对象、机制、数据、条件、关系和术语。

### 页面结构
- 主信息：
- 次信息：
- 图表 / 流程 / 对比 / 关系：
- 页面结论或收束：

### 内容依据
- 来源位置：
- 关键事实或证据：
- 限定条件 / 不确定项：

### 页面表达
本页适合的构图、素材、图形关系和动效建议。
```

字段可按材料调整，不要求所有页面完全相同。

### 4.5 页面规划稿的硬性要求

- 不能只写“标题 + 3~5 个关键词”；
- 页面正文必须具备足够信息密度，接近最终 PPT 可用文案；
- 具体机制不能被抽象动词替换；
- 关键流程要保留参与者、输入、处理和输出；
- 架构页要保留职责、接口或数据关系，而不是只有层级名称；
- 价值或效果必须有材料中的机制、指标或结果支撑；
- 会影响理解的条件、权限、性能、安全、异常和边界不能因“页面简洁”而消失；
- 每页要知道自己的信息从哪里来；
- 编辑性连接语、总结和归纳不能冒充源文档事实。

## 5. 现成大纲路径：直接进入演示设计

如果用户只提供已经整理好的 PPT 大纲，不执行一次新的“事实底稿 → 内容地图 → 再生成大纲”。

先完整阅读全部大纲，理解：

- 页面范围；
- 章节顺序；
- 核心业务对象；
- 页面之间的依赖；
- 哪些内容是正文；
- 哪些内容是设计、排版、素材或禁用词说明；
- 用户已经作出的取舍。

然后直接建立最终页面设计方案。

对于接近逐页成稿的 Markdown：

- 正文可以在不改变原意的情况下精炼；
- 设计提示不得误当成页面正文；
- 禁用词、边界和注意事项必须执行；
- 不要为了统一格式把不同性质的页面都改成同一种结构；
- 不要重新摘要一次，避免二次信息损失。

## 6. 内容充分性闸门

进入视觉设计前，内容必须通过以下检查。

### 通过条件

- 去掉页码和视觉形式后，仍能看出材料具体描述了什么；
- 每页存在明确对象、机制、关系、证据或结论，而不是只剩概念词；
- 流程页包含实际参与者、输入、处理和输出；
- 架构页包含职责、接口或数据关系；
- 数据页有单位、口径或来源信息；
- 价值和效果有事实或机制支撑；
- 重要限定条件没有因排版被静默删掉；
- 页数来自内容需要，而不是人为凑数；
- 页面标题没有夸大材料结论。

### 不通过条件

出现以下任一情况，应回到内容规划修正：

- 先确定整齐结构再寻找材料佐证；
- 大量页面只剩宣传口号；
- 每个一级标题机械变成一页；
- 每段材料都被摘要成一个卡片；
- 使用“全面、智能、高效、一体化、赋能、闭环”等词替代真实内容；
- 为了有“完整故事”擅自增加材料没有支撑的行业判断、价值承诺或愿景；
- 为了排版简单而删除难以放置的信息；
- 中间规划稿比源文档明显丢失关键事实。

## 7. 分析演示目标与视觉参考

开始设计前，将用户需求转化为明确标准：

- 核心信息；
- 受众；
- 演示场景；
- 受众知识水平；
- 语气、能量、密度和正式程度；
- 品牌规则；
- 风格关键词；
- 必须保留的内容；
- 允许改变的内容；
- 时长、页数和交付形式；
- 参考图或参考演示文稿。

分析视觉参考时关注可迁移特征：

- 构图和留白；
- 字体和层级；
- 色彩关系；
- 图形语言；
- 图片处理；
- 信息密度；
- 数据可视化；
- Logo、页码和 chrome；
- 动效节奏。

参考图默认提供视觉语言，不自动成为每页固定布局模板。

除非用户明确要求复刻，否则不得把参考页中的具体模块机械搬到其他内容页。

## 8. 从内容到最终演示文案

最终页面文案要在“准确”和“可演示”之间取得平衡。

规则：

- 保留准确名称、指标、单位、限制条件和关键业务关系；
- 标题优先使用准确主题或有材料支撑的判断；
- 不把中性说明加工成夸张宣传语；
- 正文优先回答“是什么、如何运行、由什么支撑、边界在哪里”；
- 抽象价值词只有在页面能解释其机制时才保留；
- 可通过图形表达的关系，不重复堆积同义长文字；
- 内容过密时先重写、重组或拆页，不通过缩小所有字号解决；
- 不使用程序化固定字数截断；
- 不使用省略号隐藏未处理内容；
- 不因为某段内容难排版就静默删除。

### 从源文档开始时

每页最终文案必须同时核对：

1. 页面级内容规划稿；
2. 对应源文档原始内容。

页面规划稿负责组织，源文档负责事实。

### 从现成大纲开始时

大纲负责内容范围和用户编辑判断。

可以重写表达，但不得改变实质内容、删除用户明确保留的信息或补造事实。

## 9. 整套演示结构

在编码前建立简洁的页面清单，至少明确：

- 页码和页面标题；
- 页面目的；
- 主信息和次信息；
- 页面关系类型：总览、流程、对比、架构、时间线、数据、案例、说明等；
- 适合的视觉结构；
- 必要素材；
- 动效判定：必需 / 可选 / 静态。

不要再创建一套与页面级内容规划稿高度重复的完整 slide map 文档。

整套检查：

- 开场是否快速建立主题和重点；
- 页面之间逻辑是否自然；
- 是否存在必要的章节过渡；
- 页面密度是否有节奏；
- 构图是否过度重复；
- 关键页面是否得到足够强调；
- 结尾是否真正收束整套内容。

---

## 10. 首页设计硬性要求

首页不是普通标题页，必须作为整套演示最重要的视觉入口单独设计。

首页必须：

- 突出整套演示最重要的主题、核心命题或对象；
- 建立一个明显视觉焦点；
- 让观众在短时间内知道“这套 PPT 主要讲什么”；
- 有明确的层级和设计感；
- 与整套视觉系统一致，但允许比普通内容页更大胆；
- 在需要时使用主视觉、关键数字、核心结构、产品界面、业务场景图、系统关系或图形化命题来增强表达。

首页不能只是：

- 大标题 + 小副标题 + Logo；
- 一块普通矩形卡片；
- 大量装饰但没有内容重点；
- 和后续普通内容页完全同构的模板页面。

首页可以包含：

- 强主标题；
- 简洁副标题；
- 一句有材料支撑的核心命题；
- 关键数字或关键能力；
- 主视觉图形；
- 产品 / 系统 / 场景图；
- 必要的汇报对象、单位、日期等信息。

不要为了“设计感”编造数据、口号或价值判断。

## 11. 主体页面设计

根据内容关系选择构图，可以使用：

- 主张页；
- 编辑式分栏；
- 流程图；
- 系统架构图；
- 时间线；
- 对比；
- 数据故事；
- 图文组合；
- 带标注截图；
- 案例页；
- 全幅视觉；
- 表格；
- 矩阵；
- 地图或空间关系；
- 其他真正适合内容的结构。

这些是表达手段，不是预设模板。

每页应做到：

- 有一个清晰视觉焦点；
- 有明确阅读顺序；
- 通过比例、位置、对比和空间建立层级；
- 聚合相关内容，分隔无关内容；
- 让图形、箭头、线条和色彩表达真实关系；
- 保留必要标签、单位和限定条件；
- 控制无关装饰；
- 在演示距离下仍然可读；
- 不因追求“简洁”而变空。

逐页自问：

> 去掉标题后，这个布局是否仍能体现本页独有的信息关系？

如果只是上一页换了标题和文字，应重新设计。

---

## 12. 最后一页设计硬性要求

最后一页必须同时承担：

1. **总结整套演示；**
2. **完成结束和感谢。**

不能只显示“谢谢观看 / THANKS”。

最后一页应根据演示类型收束：

- 核心结论；
- 最重要的能力组合；
- 关键成果；
- 决策点；
- 下一步行动；
- 项目目标；
- 关键原则；
- 用户最终应记住的 1~3 个重点。

然后以简洁方式表达感谢。

如果用户提供了联系人、邮箱、二维码或单位信息，可以合理放置；用户没有提供时不得虚构。

最后一页应该有结束感，但不能与前文脱节，也不能突然变成纯装饰页面。

---

## 13. Design System

Create Mode 在主要页面设计方向明确后提取 Design System；Revise Mode 优先识别已有系统。

### 13.1 画布与网格

- 1920 × 1080；
- 16:9；
- 定义安全边距、内容边界、列和基础间距；
- 关键内容远离画布边缘；
- 保持共同对齐锚点，同时允许不同页面有不同构图。

### 13.2 字体

定义合理的：

- 展示标题；
- 页面标题；
- 正文；
- 数据；
- 标签；
- 图注；
- 脚注。

要求：

- 控制字体家族和字重数量；
- 保证中文和数字显示稳定；
- 避免孤行、异常换行和字符裁切；
- 正文和标签不能小到只能近距离阅读；
- 字体必须本地可用或作为项目资源提供可靠 fallback。

### 13.3 色彩

定义：

- 背景；
- 表面；
- 正文；
- 次要文字；
- 强调色；
- 状态色；
- 数据系列色。

同类含义跨页保持颜色语义一致。

### 13.4 形状与图形语言

建立统一的：

- 间距尺度；
- 圆角；
- 描边；
- 分隔线；
- 阴影；
- 图标风格；
- 箭头；
- 连接线；
- 强调线；
- 必要的光效或纹理。

不要只靠“深色背景 + 圆角卡片”制造设计感。

### 13.5 Global Chrome

统一：

- Logo；
- 页码；
- 章节标识；
- 页脚；
- 来源行；
- 进度提示。

只使用场景真正需要的 chrome。

封面、章节页、全幅视觉和最后一页可以按设计目的调整或隐藏部分 chrome。

### 13.6 图像和数据可视化

- 保持合理裁切和比例；
- 图片风格尽量统一；
- 图表必须有可读单位、标签和必要来源；
- 能直接标注时优先直接标注；
- 图解服务理解，不作为装饰；
- 禁止低质量拉伸图片。

---

## 14. 动效

逐页将动效标记为：

- **必需**；
- **可选**；
- **静态**。

### 14.1 动效应服务内容关系

流程、时间线、因果链、层级展开、关系网络、数据流、图表增长、步骤操作、地图路径或前后状态变化，通常适合元素级动效。

封面、单一主张、简短总结、声明或一眼可读的静态构图可以保持静态。

### 14.2 网页动效实现要求

- 全局翻页 transition 不算页面内容动效；
- 离散步骤可使用框架 fragment、CSS 状态类或自定义 JavaScript 状态机；
- 连续路径、连线和图表可使用 CSS、Web Animations API、SVG 动画或 Canvas/WebGL；
- 如果开发阶段使用 Reveal.js，可使用其 `ready`、`slidechanged`、`fragmentshown`、`fragmenthidden` 等事件；
- 如果使用其他框架或自研翻页逻辑，应提供等效、可靠的页面进入、离开、前进、后退和重播事件；
- 不依赖固定延时猜测页面状态；
- 动画最终状态必须与静态最终版一致；
- 返回页面、后退、重新进入和直接打开指定页面时状态必须正确；
- 快速连续翻页不能留下半完成状态；
- 必须支持 `prefers-reduced-motion`；
- 减少动态效果时直接呈现完整可读最终状态。

动效不应暗示材料中不存在的数据变化、交互或实时能力。

---

## 15. 网页 PPT 实现要求

使用语义清晰、可维护的 HTML、CSS 和必要 JavaScript。开发阶段可以选择最合适的实现方式，例如：

- 原生 HTML / CSS / JavaScript；
- Reveal.js；
- Vite + 自定义页面框架；
- 其他适合静态构建输出的前端方案。

**实现框架不是最终交付依赖。** 最终交付只看构建后的静态产物能否独立运行。

页面实现必须：

- 使用 1920 × 1080、16:9 的设计基准；
- 包含全部计划页面；
- 默认采用水平演示顺序，除非用户明确要求其他结构；
- 使用清晰 DOM 顺序；
- 限制演示专用样式作用范围；
- 用 CSS 自定义属性表达稳定 Design Tokens；
- 在合适场景使用共享组件；
- 避免为了抽象而建立比演示稿本身更复杂的组件系统；
- 信息性图片具有合理替代文本；
- 装饰图片不干扰阅读顺序；
- 稳定布局可用时避免脆弱绝对定位；
- 艺术化构图需要时可以有意绝对定位；
- 不保留 lorem ipsum、占位图、未完成容器、TODO 页面或虚构数据。

如果使用 Reveal.js 或其他演示框架，可以在开发源码中保留其结构与 API；但这些依赖必须在最终 build 中被打包、复制或内联，不能要求目标机器再次安装。

---

## 16. 最终构建与独立运行

最终网页 PPT 必须以**构建后的静态产物**交付。

这意味着：

- 开发阶段可以安装并使用 Reveal.js、Node.js、npm、pnpm、yarn、Vite、Webpack、Parcel 等工具；
- 最终运行阶段不得要求再次安装这些工具；
- 最终产物必须已经包含页面运行所需的 HTML、CSS、JavaScript、图片、图标、字体和其他资源；
- 将最终输出目录整体复制到另一台机器后，应仍然可以运行。

### 16.1 推荐的最终输出结构

最终输出可以是：

```text
dist/
├── index.html
├── assets/
│   ├── *.js
│   ├── *.css
│   ├── images/
│   ├── icons/
│   └── fonts/
└── README.md        # 可选
```

也可以是单文件 `index.html`。

除非用户明确要求单文件，否则**多文件静态产物完全可接受**；重点是输出目录完整、自包含、无需再构建。

### 16.2 最终产物不得依赖

最终 `dist` / 输出目录不得引用：

- `node_modules`；
- `src/`、开发源码目录或未构建模块；
- Vite / Webpack / npm dev server；
- 开发机绝对路径；
- `/mnt/...`、临时工作目录；
- `localhost` 上其他开发服务；
- 在线 CDN；
- Google Fonts 或其他在线字体服务；
- 运行时远程拉取的 Reveal.js、插件、图标库、JavaScript、CSS、图片或字体；
- 只有制作者电脑上才存在的文件。

禁止在最终 HTML 中出现类似：

```text
/node_modules/...
/src/...
http://localhost:5173/...
https://cdn.jsdelivr.net/...
C:\...
/mnt/data/...
```

### 16.3 Reveal.js 的处理

如果开发阶段使用 Reveal.js：

- 可以通过 npm 安装；
- 可以由 Vite / Webpack 等构建；
- 也可以手工放在开发项目中；
- 但最终产物必须已经包含 Reveal.js 运行所需代码；
- 目标机器**不需要安装 Reveal.js**；
- 最终产物不能直接引用 `node_modules/reveal.js/...`；
- 最终产物不能依赖 Reveal.js CDN。

Reveal.js 在这里是**开发/构建实现选项**，不是用户运行演示稿时必须具备的环境。

### 16.4 无网络运行

断开外网后，通过普通静态 HTTP 服务，以下内容仍必须完整可用：

- 页面；
- 样式；
- 图片；
- 字体；
- 图标；
- JavaScript；
- 页面导航；
- 动效；
- 图表和图解；
- 使用到的演示框架运行时代码。

如果视觉效果依赖特殊字体，应将合法可分发的字体打包进最终产物；否则使用可靠系统字体栈和合适 fallback。

### 16.5 运行方式

最终产物不需要任何 build 命令。

只需在输出目录启动任意静态 HTTP 服务，例如：

```bash
python -m http.server 8000
```

然后访问：

```text
http://localhost:8000/
```

也可以部署到 Nginx、Apache、对象存储静态网站、GitHub Pages 或其他普通静态托管环境。

### 16.6 单文件模式

如果用户明确要求“只有一个 HTML 文件”，则进一步将 CSS、JavaScript 和可嵌入资源内联，尽可能形成真正单文件交付。

如果用户只要求“独立运行”或“不要安装 Reveal.js”，则不需要强制单文件；完整的静态 `dist` 目录即可。

## 17. 最终构建产物验证

QA 必须针对**最终构建后的输出目录**，不能只验证开发服务器。

至少验证：

- 从最终输出目录启动静态 HTTP 服务后首页正常加载；
- 所有页面可前进、后退；
- 直接进入指定页面或深链时行为正常；
- 刷新后状态合理；
- 字体、图片、图标、图表正常加载；
- 断网后演示仍完整可用；
- 动效和页面状态正常；
- 浏览器控制台没有影响演示的资源错误；
- Network 中没有意外访问 CDN、开发服务器或本地绝对路径；
- 最终目录整体复制到其他位置后仍可运行。

不能只验证：

- Vite / npm dev server；
- 源码目录；
- `node_modules` 环境；
- 开发机上的临时地址；
- 阅读源代码或 DOM。

真实浏览器中的最终构建结果才是交付依据。

## 18. 内容完整性检查

维护一份轻量内容检查清单。

### 源文档输入

检查：

- 源文档重要内容是否映射到页面级内容规划稿；
- 最终页面是否仍可追溯到对应源文档内容；
- 名称、数字、日期、单位和标签是否准确；
- 关键机制和业务关系是否保留；
- 输入输出、依赖、异常、权限、性能、安全和验收边界是否被保留；
- 编辑归纳是否被误写成原文事实；
- 是否因排版困难而漏掉信息。

### 现成大纲输入

检查：

- 用户要求保留的页面和内容是否都存在；
- 页面顺序是否保持用户确定的逻辑；
- 实质内容是否被过度摘要；
- 具体机制是否被口号化；
- 设计提示是否被误当成正文；
- 用户明确的禁用词和边界是否得到遵守。

### 所有模式

检查：

- 图注、图例和视觉内容一致；
- fragment 最终状态内容完整；
- 首页是否准确代表整套演示；
- 最后一页是否真正总结了全套内容；
- 不存在固定 N 项截断或固定字数截断。

---

## 19. QA 工作流

QA 分为制作期快速检查和最终验收。

### 19.1 制作阶段

优先在真实浏览器中快速预览。

重点检查：

- 页面构图；
- 内容密度；
- 文本换行；
- 图片裁切；
- 元素对齐；
- 字体加载；
- 动效触发；
- 浏览器错误。

不要求每次小修改后都重新渲染整套页面。

### 19.2 最终验收

Create Mode 完成前必须：

- 将**全部页面**以 1920 × 1080 的目标视口进行最终渲染检查；
- 每页至少检查最终可见状态；
- 高密度页、特殊构图页、首页和最后一页必须查看完整尺寸结果；
- 动效页必须实际播放验证，并检查至少一个有意义中间状态和最终状态；
- 发现问题后修改源文件并重新检查相关页面。

“渲染图片”是最终视觉验收的证据，而不是为了完成流程生成的无意义工件。

### 19.3 Contact Sheet

Contact sheet 用于 Deck-Level QA，主要检查：

- 页面节奏；
- 密度变化；
- 色彩分布；
- 构图重复；
- 风格跳变；
- 章节过渡；
- 页面缺失或重复。

Create Mode 推荐生成整套 contact sheet；当页面较多、风格复杂、全局样式发生变化或需要整体节奏判断时，应生成并检查。

局部 Revise Mode 不要求为了形式强制生成完整 contact sheet。

---

## 20. Slide-Level QA

逐页查看受影响的完整尺寸渲染结果，检查：

- 视觉焦点；
- 阅读顺序；
- 文本层级；
- 换行、孤行、截断和裁切；
- 过密段落；
- 间距、对齐和平衡；
- 光学居中；
- 图片质量、比例和主体位置；
- 图表标签、单位、图例和来源；
- Logo、页码、页脚和来源位置；
- 意外相切、重叠和边缘拥挤；
- 图标、箭头和颜色是否具有明确语义；
- fragment 最终状态是否完整；
- 动效初始状态是否保留必要上下文；
- 中间状态是否具有清晰焦点；
- 前进、后退和重新进入是否正确；
- `prefers-reduced-motion` 下是否直接得到完整可读页面。

特别检查：

- 首页；
- 章节转换页；
- 高密度页面；
- 非标准构图页面；
- 最后一页。

不能只看缩略图判断单页质量。

---

## 21. Deck-Level QA

通过连续播放和必要的 contact sheet 检查：

- 叙事流；
- 章节结构；
- 首页是否建立核心主题；
- 页面间视觉节奏；
- 字体、颜色、间距、图形和 chrome 的统一性；
- 是否有足够布局变化；
- 密度是否均衡；
- 关键观点是否突出；
- 转场和动效是否一致；
- 最后一页是否完成总结和感谢；
- 整套演示是否具有共同视觉身份。

一致性不等于所有页面结构相同。

---

## 22. 自动布局检查

在字体和资源加载完成后，以 1920 × 1080 目标视口对所有相关页面进行自动检查。

至少检查：

- 元素是否越界；
- 是否出现意外 horizontal / vertical overflow；
- 文本或媒体是否被容器裁切；
- 是否存在 CSS 省略号或固定长度截断；
- 是否存在非预期重叠；
- 图片、图表或嵌入资源是否缺失或尺寸为零；
- 是否有资源请求失败；
- 是否有影响网页演示运行的控制台错误；
- 是否有重复 ID 或无效页面结构；
- 页面数量是否与规划一致；
- 标记为必需动效的页面是否真的存在 fragment 或动画挂钩；
- 动效页初始、中间和最终状态是否发生越界或重叠；
- 深链、前进、后退和重新进入后状态是否一致；
- 减少动态效果模式是否显示完整内容。

可使用：

- bounding box；
- 文本节点范围；
- computed style；
- scrollWidth / scrollHeight；
- 图片 natural size；
- 字体和资源加载状态；

辅助判断。

自动检查不能替代真实视觉检查。

## 23. Revise Mode 的影响范围

### 23.1 局部页面修改

例如：

- 一处文字；
- 单页换图；
- 单页排版；
- 单页动效。

要求：

- 修改目标页面；
- 重新渲染受影响页面；
- 检查内容和布局；
- 若影响相邻叙事，再检查前后页。

### 23.2 共享组件修改

例如：

- 标题组件；
- 卡片；
- 图表结构；
- 页脚；
- 共享图形。

要求：

- 找出所有使用位置；
- 修改共享实现；
- 重新检查所有受影响页面；
- 必要时进行 deck-level QA。

### 23.3 全局 Design System 修改

例如：

- 字体；
- 颜色；
- 间距；
- 网格；
- 背景；
- Logo；
- 全局 chrome；
- 通用动效。

要求：

- 更新全局 token；
- 重新渲染全部页面；
- 执行完整视觉和自动布局回归检查；
- 检查整套节奏和一致性。

### 23.4 叙事或结构修改

例如：

- 增删页面；
- 调整顺序；
- 重构章节；
- 拆分或合并内容。

要求：

- 更新受影响页面规划；
- 检查内容映射；
- 检查页码、导航和章节标识；
- 如果整套节奏受到影响，重新执行 Deck-Level QA。

如果影响范围不确定，按最大合理影响范围检查。

## 24. 修改与复验

发现问题后：

1. 定位负责问题的内容、HTML、CSS、JavaScript 或素材；
2. 修改源文件；
3. 重新渲染所有受影响页面；
4. 查看完整尺寸结果；
5. 重新运行相关自动检查；
6. 共享和全局变化时扩大回归范围；
7. 重复直到没有实质问题。

不要只通过阅读代码判断问题已经解决。

## 25. 完成标准

### 25.1 只要求内容规划稿

如果用户只要求从源文档生成演示内容规划，完成标准是：

- Markdown 文件已生成；
- 页面级内容不是关键词摘要；
- 核心事实和来源可核对；
- 页面顺序合理；
- 关键限制没有丢失。

此时不继续制作演示稿。

### 25.2 Create Mode 完整任务

只有以下条件全部满足才算完成：

- 已正确识别内容权威来源；
- 源文档输入时已生成页面级内容规划稿；
- 现成大纲输入时没有进行不必要的二次摘要重构；
- 所有页面都已实现；
- 首页突出重点并具有明确设计感；
- 主体页面内容完整、准确且不空泛；
- 最后一页完成总结和感谢；
- Design System 在整套演示中一致；
- 页面构图根据内容关系选择，而非统一套模板；
- 必需的元素级动效已经实现；
- `prefers-reduced-motion` 正常；
- 最终交付为构建后的静态网页产物，运行端无需任何前端构建环境；
- 已通过本地 HTTP 地址验证；
- 全部页面已进行最终真实渲染检查；
- 高风险页面已查看完整尺寸结果；
- 动效页面已播放验证；
- 内容、视觉和自动布局检查通过；
- 所有实质问题已在源文件中修复并重新验证。

### 25.3 Revise Mode 完整任务

只有以下条件全部满足才算完成：

- 用户要求已落实到源文件；
- 未要求修改的关键内容没有被意外改变；
- 当前 Design System 已被识别并合理保留或更新；
- 所有受影响页面已重新渲染并检查；
- QA 范围与修改影响范围匹配；
- 共享或全局修改已执行跨页回归；
- 构建后的静态网页产物仍然完整、自包含并可独立运行；
- 所有实质问题已通过重新渲染验证。

## 26. Final Rules

1. 用户当前要求和明确取舍优先于通用演示习惯。
2. 开始前先确定内容权威来源。
3. 只有源文档时，源文档全过程保持事实权威地位；中间稿不能替代源文档。
4. 只有现成大纲时，大纲是内容权威来源；默认尊重用户已经完成的内容规划。
5. 源文档 + 大纲同时存在且用户未指定时，大纲管结构和重点，源文档管事实和证据。
6. 源文档生成的中间稿必须是页面级内容规划稿，而不是摘要式标题列表。
7. 不建立高度重复的事实底稿、内容地图和 slide map 文档来增加流程负担。
8. 不使用空泛价值词替代具体业务内容。
9. 不因为排版困难静默删除信息。
10. 内容决定布局，不提前套固定页面模板。
11. 首页必须突出整套演示的核心重点和视觉焦点，并具有明确设计感。
12. 最后一页必须同时承担总结和感谢，不能只有“谢谢观看”。
13. 采用 1920 × 1080、16:9 的网页演示画布。
14. 最终交付必须是构建后的静态网页产物；目标机器无需安装 Reveal.js、Node.js、npm、Vite、Webpack 或其他构建环境，并可在无外网环境下通过任意静态 HTTP 服务运行。
15. 用户明确要求单文件时，进一步制作真正单 HTML 交付。
16. 制作阶段使用浏览器快速预览；最终交付前必须完整检查全部页面真实渲染结果。
17. Contact sheet 是 Deck-Level QA 工具，不为了形式强制生成无意义工件。
18. 自动检查用于发现问题，不能替代视觉检查。
19. 发现问题必须修改源文件并重新渲染验证。
20. 只有内容完整、设计有效、运行独立、最终渲染和相应回归检查全部通过后，任务才算完成。
